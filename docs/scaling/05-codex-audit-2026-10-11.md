## Executive summary

The codebase passes its existing tests, but has confirmed defects in authorization, session handling, message delivery, pagination, privacy, and test tooling. Several affect normal use; the seed maintenance command can delete real account data. No Critical issue was confirmed.

The audit identified 31 confirmed findings: 6 High, 22 Medium, and 3 Low. Seven additional risks require further verification. Passing tests do not cover the reproduced failures below.

Highest priorities: established-socket authorization, logout/session isolation, registration throttles, safe seed-account identification, and recovery from missing message acknowledgements.

## Using this checklist

- Re-check each finding against the commit you intend to fix.
- For each fix, first add a regression test that reproduces the reported failure.
- Mark an item complete only after the correction and its regression check pass.
- Keep deployment-dependent risks separate from confirmed implementation defects.
- Follow the repository's branch, PR, test, and learning-journal requirements when implementing fixes.

## Confirmed High-severity issues

### [ ] H-01 — Established WebSockets retain authorization after disabling and token expiry

**Severity:** High.  
**Location:** `chats/middleware.py:13`, `user_from_token`; `chats/consumers.py:102`, `InboxConsumer.receive`.

**Problem / root cause:** Authentication checks `is_active` and token validity only during connection establishment. Later frames use the cached user without checking either again.

**Impact:** Disabling an account prevents new connections but does not stop its existing socket. An expired access token can continue authorizing messages through that socket.

**Recommended fix:** Enforce socket expiry and revalidate account status at a bounded interval or before protected operations. Close sockets when authorization becomes invalid.

**Verification:** Connected with a two-second token, disabled the account, waited past expiry, and successfully sent a message through the established socket.

### [ ] H-02 — IP throttles accept a client-controlled forwarding identity

**Severity:** High.  
**Location:** `accounts/throttles.py:5`, `LoginIPThrottle`; `root/settings.py:179`, `REST_FRAMEWORK`.

**Problem / root cause:** Throttles use DRF's default client identification without a configured trusted proxy policy. Changing `X-Forwarded-For` changes the throttle identity.

**Impact:** One client can bypass IP-based login limits if the incoming header is not sanitized by a trusted proxy.

**Recommended fix:** Configure client identification for the actual deployment. Direct connections should ignore supplied forwarding headers; proxy deployments should trust only sanitized headers from known proxies.

**Verification:** Sent 21 failed logins with the same `REMOTE_ADDR` and different forwarding headers. The twenty-first returned `401`, rather than a throttle rejection. Actual production proxy sanitization was not verified.

### [ ] H-03 — Registration's IP limit becomes a per-account limit with a JWT

**Severity:** High.  
**Location:** `accounts/views.py:26`, `RegisterCreateAPIView`.

**Problem / root cause:** Registration uses `ScopedRateThrottle` with JWT authentication enabled. Authenticated requests are keyed by user ID instead of IP.

**Impact:** After exhausting anonymous registration allowance, a client can continue through authenticated identities. Newly created accounts provide additional throttle identities.

**Recommended fix:** Use a registration throttle always keyed by the trusted client IP, independently of authentication.

**Verification:** After five successful anonymous registrations from one IP, another registration from that IP using an existing account's JWT returned `201`.

### [ ] H-04 — Logout does not invalidate outstanding session work

**Severity:** High.  
**Location:** `assets/app.js:49`, `refreshAccess`; `:169`, `loadChats`; `:375`, `closeSocket`; `:585`, `logout`.

**Problem / root cause:** Requests, refresh operations, socket callbacks, and reconnect timers lack a session-generation guard. Logout also leaves pending-send and some conversation state behind.

**Impact:** An old refresh can restore credentials after logout or replace newer credentials. Old responses can install the previous account's data. A pending send can block messaging after another login.

**Recommended fix:** Introduce a session generation checked before every asynchronous state update. Cancel reconnect timers, detach socket callbacks, and clear pending-send, conversation, and rendered-message state during logout.

**Verification:** Controlled frontend executions reproduced an old refresh restoring a token after logout, an old chat response populating a newer session, and a retained pending send preventing another send.

### [x] H-05 — Load-test seeding can delete real users even on invalid invocation

**Severity:** High.  
**Location:** `chats/management/commands/loadtest_seed.py:26`, `loadtest_users`; `:47`, `Command.handle`.

**Problem / root cause:** Seed accounts are identified by a real phone-number prefix and the user-controlled name `loadtest`. Matches are deleted before argument validation and outside the replacement transaction.

**Impact:** A legitimate matching account can be deleted, cascading to conversations and messages. Invalid arguments can trigger deletion without creating replacements.

**Recommended fix:** Validate every argument before mutation. Use authoritative fixture identification or an isolated load-test database. Make replacement transactional.

**Verification:** In an isolated database, created a matching ordinary account and invoked the command with `users=0`. It raised `CommandError`, but the account had already been deleted.

### [ ] H-06 — A missing message echo can permanently block sending

**Severity:** High.  
**Location:** `assets/app.js:457`, acknowledgement handling; `:534`, submission handler.

**Problem / root cause:** `state.sending` blocks every later send until an echo, error, or socket-close event clears it. There is no acknowledgement timeout. Heartbeats do not enforce a response deadline.

**Impact:** A dropped notification or stalled connection can block messaging across conversations while the socket still appears open.

**Recommended fix:** Bound acknowledgement waiting, reconcile uncertain sends against persisted history, and enforce connection liveness. Use correlation or idempotency identifiers to avoid blind duplicate retries.

**Verification:** With an open socket and no echo, two submissions produced only one frame; pending state remained set.

## Confirmed Medium-severity issues

### [ ] M-01 — The five-socket limit is not atomic

**Severity:** Medium.  
**Location:** `chats/consumers.py:64`, `InboxConsumer.connect`.

**Problem / root cause:** Counting sockets and registering a new one are separate operations.

**Impact:** Concurrent connections can exceed the intended limit.

**Recommended fix:** Atomically prune, count, and admit sockets in Redis; clean up admission when connection establishment fails.

**Verification:** Eight simultaneous connections for one user were admitted and answered pings despite the five-socket limit.

### [ ] M-02 — Long-lived sockets lose notification-group membership

**Severity:** Medium.  
**Location:** `chats/consumers.py:76`, group registration; `:122`, ping handling.

**Problem / root cause:** Membership is added once. Pings refresh presence but not channel-layer group membership. The installed Redis channel layer expires membership after 24 hours by default.

**Impact:** A socket can remain connected and responsive while no longer receiving group notifications.

**Recommended fix:** Renew membership periodically or enforce a connection lifetime shorter than group expiry.

**Verification:** Using real Redis with a shortened expiry, delivery worked before expiry and stopped afterward.

### [ ] M-03 — Reconnect recovery can permanently miss messages

**Severity:** Medium.  
**Location:** `assets/app.js:315`, `catchUp`; `:424`, readiness handling.

**Problem / root cause:** Recovery starts after the largest observed ID. A missing earlier notification is excluded after a later notification arrives. Initial readiness also does not recover the history-to-subscription gap.

**Impact:** Persisted messages can stay absent until history is reloaded.

**Recommended fix:** Recover from an authoritative synchronization boundary, reconcile an overlapping range, and recover on initial readiness as well as reconnects.

**Verification:** With IDs `1` and `3` locally present, recovery requested `after=3`, excluding missing ID `2`. Source tracing confirmed the initial connection path does not close the history/subscription gap.

### [ ] M-04 — Broadcast failure reports failure after successful persistence

**Severity:** Medium.  
**Location:** `chats/views.py:116`, `MessageListCreateAPIView.perform_create`; `chats/consumers.py:159`, socket persistence/broadcast path.

**Problem / root cause:** Persistence completes before broadcasting; broadcast exceptions propagate as request or consumer failures.

**Impact:** Senders receive failure for saved messages. Retrying can create duplicates.

**Recommended fix:** Separate persistence acknowledgement from notification delivery, handle notification failures explicitly, and provide safe reconciliation or idempotent retry.

**Verification:** Forced broadcasting to raise a Redis connection error. REST creation raised an exception while the message remained stored.

### [ ] M-05 — WebSocket input can crash parsing or persistence

**Severity:** Medium.  
**Location:** `chats/consumers.py:110`, JSON parsing; `:141`, text validation.

**Problem / root cause:** Parsing catches only `JSONDecodeError`; oversized integers can raise `ValueError`. Text validation permits NUL characters and invalid Unicode surrogates rejected by REST validation.

**Impact:** Invalid client input can crash handling or produce database/encoding errors instead of controlled validation responses.

**Recommended fix:** Handle bounded parser failures and share text validation between REST and WebSocket paths.

**Verification:** A 5,000-digit JSON integer raised `ValueError`. PostgreSQL rejected NUL-containing text; invalid surrogates raised encoding errors. Deep nesting was not confirmed as a failure on the installed Python version and is not included as a confirmed bug.

### [ ] M-06 — Read receipts include messages never displayed

**Severity:** Medium.  
**Location:** `chats/consumers.py:214`, `mark_read`; `chats/views.py:135`, `MarkChatReadAPIView.post`; `assets/app.js:472`, receipt handling.

**Problem / root cause:** Reads mark all unread messages without a displayed-message boundary. The frontend applies receipts to all outgoing messages.

**Impact:** Concurrently arriving or undelivered messages can be reported as read.

**Recommended fix:** Send the highest displayed-message boundary; update and broadcast only messages covered by it.

**Verification:** Created a displayed message followed by an undisplayed message. One read request marked both read.

### [ ] M-07 — REST read operations do not notify senders

**Severity:** Medium.  
**Location:** `chats/views.py:135`, `MarkChatReadAPIView.post`.

**Problem / root cause:** REST updates the database without broadcasting the read notification used by the socket path.

**Impact:** Connected senders see stale receipt state.

**Recommended fix:** Share read-update and notification logic between transports.

**Verification:** With the sender connected, REST marked the message read but delivered no socket notification.

### [ ] M-08 — Reconnection does not repair missed read receipts

**Severity:** Medium.  
**Location:** `assets/app.js:315`, `catchUp`; `:286`, `appendMessage`.

**Problem / root cause:** Recovery fetches new messages only. Existing rendered messages are not refreshed; duplicate suppression does not reconcile changed receipt fields.

**Impact:** Receipts missed during disconnection remain stale after reconnection.

**Recommended fix:** Reconcile visible message receipt state or retrieve the authoritative read boundary during recovery.

**Verification:** Source tracing found no reconnect operation reloading existing messages' changed `is_read` values.

### [ ] M-09 — History and live responses render out of order

**Severity:** Medium.  
**Location:** `assets/app.js:301`, `loadHistory`; `:453`, live-message handling.

**Problem / root cause:** History and live notifications append independently instead of merging into an ordered collection.

**Impact:** A live message arriving before initial history appears above older messages.

**Recommended fix:** Buffer live arrivals during loading or merge and sort consistently before rendering.

**Verification:** Delivered live ID `103`, then history containing `102` and `101`; rendered order became `[103, 101, 102]`.

### [ ] M-10 — Pagination advances on concurrency and failure

**Severity:** Medium.  
**Location:** `assets/app.js:178`, chat pagination; `:324`, older-message pagination.

**Problem / root cause:** Concurrent sidebar requests can fetch the same page and advance twice. History advances before confirming success.

**Impact:** Pages are skipped; failed history loading moves the next attempt past the failed page.

**Recommended fix:** Serialize each pagination stream, disable controls during loading, and advance only after success.

**Verification:** Concurrent sidebar requests produced `2, 2, 4`. Failed history page `2` was followed by page `3`.

### [ ] M-11 — New messages destabilize offset history pagination

**Severity:** Medium.  
**Location:** `chats/views.py:99`, `MessageListCreateAPIView.get_queryset`; `assets/app.js:301`, `loadHistory`.

**Problem / root cause:** Offsets address a newest-first collection that shifts with inserts.

**Impact:** Loading older history can return already loaded messages and make no visible progress.

**Recommended fix:** Use a stable cursor before the oldest loaded message, with deterministic ordering.

**Verification:** Loaded 50 newest messages, inserted 50 more, then requested page two. It returned the same original 50 rather than older history.

### [ ] M-12 — Transient HTTP failures prevent socket startup or reconnection

**Severity:** Medium.  
**Location:** `assets/app.js:505`, close handling; `:598`, `start`.

**Problem / root cause:** Startup awaits chat loading before connecting; a rejection aborts that sequence. Reconnect refresh rejection also lacks recovery handling.

**Impact:** The UI remains disconnected after transient failure, even when later polling works.

**Recommended fix:** Retry startup/reconnection independently of sidebar loading. Distinguish network failure from invalid credentials and handle rejected promises.

**Verification:** Profile loading succeeded, chat loading failed, and zero socket connections were attempted. Later successful polling did not connect it.

### [ ] M-13 — Presence and unread state remain stale in displayed conversations

**Severity:** Medium.  
**Location:** `assets/app.js:169`, `loadChats`; `:333`, `openChat`; `:615`, polling.

**Problem / root cause:** Polling refreshes the first page while retaining older cached entries. The active presence header is set on opening rather than refreshed afterward.

**Impact:** Active headers and conversations beyond the first page show outdated state.

**Recommended fix:** Refresh the active participant/header and reconcile state for displayed cached conversations.

**Verification:** Source tracing confirmed polling updates neither the active header nor retained entries beyond the fetched page.

### [ ] M-14 — Chat serialization bypasses profile-blocking privacy

**Severity:** Medium.  
**Location:** `accounts/views.py:89`, `PublicUserAPIView.get_queryset`; `chats/serializers.py:29`, `ChatSerializer.get_participant`.

**Problem / root cause:** Direct profile access hides someone who blocked the requester, but existing chat serialization exposes their public profile and online status.

**Impact:** Blocked requesters recover information denied by the profile endpoint.

**Recommended fix:** Apply consistent participant and presence privacy rules to existing conversations.

**Verification:** Direct profile access returned `404`; the chat list returned that participant's profile and `is_online` status.

### [ ] M-15 — Avatar uploads lack application-level size limits

**Severity:** Medium.  
**Location:** `accounts/models.py:43`, `User.avatar`; `accounts/serializers.py:34`, `ProfileSerializer`.

**Problem / root cause:** Image validity is checked without explicit byte or dimension limits. Django's memory threshold moves uploads to disk rather than rejecting them.

**Impact:** Large valid uploads consume storage and processing resources.

**Recommended fix:** Enforce byte and pixel limits plus appropriate request-body limits.

**Verification:** A valid one-pixel PNG with over 6 MiB of trailing data passed serializer validation.

### [ ] M-16 — Replaced and deleted avatars leave orphaned files

**Severity:** Medium.  
**Location:** `accounts/models.py:43`, `User.avatar`; `accounts/serializers.py:34`, `ProfileSerializer`.

**Problem / root cause:** Replacing the field does not delete its previous file; account deletion has no corresponding cleanup handler.

**Impact:** Storage grows and old uploaded photographs remain retained.

**Recommended fix:** Safely delete unreferenced files after successful transactions, including account deletion.

**Verification:** Replacement saved a new file without invoking storage deletion for the old file; no deletion cleanup handler was found.

### [ ] M-17 — Password similarity validation lacks the candidate user

**Severity:** Medium.  
**Location:** `accounts/serializers.py:25`, `RegisterSerializer.validate_password`.

**Problem / root cause:** `validate_password()` receives no candidate user, preventing the configured similarity validator from comparing registration attributes.

**Impact:** Passwords matching the user's name bypass the intended validation.

**Recommended fix:** Validate against a candidate user constructed from the registration attributes.

**Verification:** A password identical to the submitted first name passed registration; validation with the candidate user rejected it.

### [ ] M-18 — Concurrent duplicate registration raises an internal error

**Severity:** Medium.  
**Location:** `accounts/serializers.py:29`, `RegisterSerializer.create`.

**Problem / root cause:** Uniqueness checking and insertion are separate; a database uniqueness violation is not translated to a validation response.

**Impact:** Concurrent registration of one phone number can return `500`.

**Recommended fix:** Catch the specific duplicate-phone constraint violation around insertion and return a field validation error without swallowing unrelated database errors.

**Verification:** Two serializers validated the same unused number. The first saved successfully; the second raised `IntegrityError`.

### [ ] M-19 — Throttle-cache outages raise unhandled authentication errors

**Severity:** Medium.  
**Location:** `accounts/views.py:25`, authentication views; `root/settings.py:104`, cache configuration.

**Problem / root cause:** Redis errors from throttle lookups propagate without an explicit availability policy.

**Impact:** Authentication returns internal errors before credential evaluation during cache failure.

**Recommended fix:** Handle backend failure deliberately, such as controlled service-unavailable responses or a bounded fallback.

**Verification:** Forced a throttle-cache lookup to raise a Redis connection error; login raised an unhandled exception.

### [ ] M-20 — OpenAPI contracts contradict actual behavior

**Severity:** Medium.  
**Location:** `accounts/authentication.py:11`, `LastSeenJWTAuthentication`; `chats/serializers.py:21`; `accounts/serializers.py:57`, `get_is_online`; `chats/views.py:131`, read response declaration.

**Problem / root cause:** The custom JWT authenticator is not recognized by the schema extension. Method fields lack accurate types. The read endpoint declares no body while returning JSON.

**Impact:** Generated clients and documentation omit authentication or use incorrect response types.

**Recommended fix:** Register the authentication extension and explicitly describe nested objects, boolean fields, and the actual read response.

**Verification:** Generation reported 13 warnings. Inspection confirmed missing security declarations and incorrect field/response definitions, despite zero schema-validation errors.

### [x] M-21 — Load-test reader errors leave dead connections counted as open

**Severity:** Medium.  
**Location:** `loadtest/run.py:103`, `SimUser.read`.

**Problem / root cause:** `self.closed = True` is after the loop rather than in `finally`; processing exceptions bypass it.

**Impact:** Capacity results count dead sockets as connected; related tasks use incorrect state.

**Recommended fix:** Set state in `finally`, record reader failures, and supervise associated tasks.

**Verification:** Acknowledgement sending raised `ConnectionResetError`. The socket was closed, but `SimUser.closed` stayed false.

### [ ] M-22 — Browser-launch errors silently skip checks and leak configuration

**Severity:** Medium.  
**Location:** `chats/test_browser.py:26`, `BrowserTestCase.setUpClass`; `:49`, `tearDownClass`.

**Problem / root cause:** Broad startup exceptions become `SkipTest`. Cleanup is not registered before startup, and the original `DJANGO_ALLOW_ASYNC_UNSAFE` value is not preserved.

**Impact:** Broken browser infrastructure can yield a green suite without browser checks; failed setup can leave Django async protection disabled for later tests.

**Recommended fix:** Fail unexpected launcher errors where browser checks are required. Register unconditional cleanup and restore the original environment value.

**Verification:** Simulated launcher failure caused a skip and left the environment value `true`. The actual full audit run successfully executed browser tests.

## Risks requiring further verification

These concerns have code or controlled-check evidence, but production impact was not established. They must not be treated as confirmed production incidents.

### [ ] R-01 — Redis exposure depends on deployment

**Priority:** High. **Location:** `compose.yaml:20`.

**Concern:** Compose declares Redis publication on all host interfaces without authentication. Public reachability depends on deployment and firewall configuration and was not established.

**Required verification / action:** Inspect effective port publication, firewall rules, and trusted networks. Remove unnecessary publication or bind privately; authenticate reachable services.

### [ ] R-02 — Concurrent REST requests can overshoot non-atomic throttles

**Priority:** Medium. **Location:** `accounts/throttles.py:5` and inherited DRF throttle behavior.

**Concern:** Cache operations are non-atomic. Independent cache snapshots reproduced the algorithmic race, but real multi-worker requests were not tested.

**Required verification / action:** Run simultaneous requests across workers against real Redis. Use atomic counters when limits must be hard guarantees.

### [ ] R-03 — Heartbeat database work can bottleneck the shared executor

**Priority:** Medium. **Location:** `chats/consumers.py:223`, `touch_last_seen`; `root/settings.py:112`, `DATABASES`.

**Concern:** Heartbeats perform frequent synchronous database work through the shared thread-sensitive executor. Default connection lifetime adds connection overhead. Execution structure was verified, but production throughput was not measured.

**Required verification / action:** Measure database connections, write volume, executor delay, and heartbeat latency. Reduce redundant writes; choose pooling or async changes based on measurements.

### [ ] R-04 — Chat-list unread aggregation processes message history repeatedly

**Priority:** Medium. **Location:** `chats/views.py:47`, chat aggregation.

**Concern:** Unread counting joins message history during repeated list requests. Generated SQL and a local query plan confirmed the structure; representative PostgreSQL latency was not benchmarked.

**Required verification / action:** Measure queries with representative histories. Consider a filtered unread subquery and suitable indexes if measurements confirm the bottleneck.

### [ ] R-05 — Ordering and recovery boundaries need concurrent-transaction testing

**Priority:** Medium. **Location:** `chats/views.py:99`, history ordering/recovery filtering.

**Concern:** Timestamp ordering has no deterministic tie-breaker. ID-based recovery assumes a safe visibility boundary despite concurrent transactions. Equal timestamps and late commits were not reproduced in a real PostgreSQL concurrency test.

**Required verification / action:** Test tied timestamps and late commits. Use deterministic ordering and an explicit synchronization contract.

### [ ] R-06 — WebSocket query credentials may enter logs

**Priority:** Medium. **Location:** `assets/app.js:412`, `connectInbox`.

**Concern:** Tokens travel in the WebSocket URL and may appear in proxy/access logs. Actual logging behavior was not inspected. No exploitable frontend XSS was confirmed.

**Required verification / action:** Inspect server/proxy logging and redact query credentials. Review credential transport for the deployed environment.

### [ ] R-07 — Unbounded message state can exhaust resources or hit argument limits

**Priority:** Low. **Location:** `assets/app.js:316`, `catchUp`, and message rendering/state.

**Concern:** Message DOM and `seenIds` grow without bounds. Spreading 200,000 IDs into `Math.max` raised `RangeError` in Node; that session size was not reproduced in a browser.

**Required verification / action:** Profile long browser sessions. Maintain a scalar recovery boundary and bound rendered history.

## Coverage and limitations

Reviewed authentication and registration, blocking/privacy, uploads, REST endpoints, WebSocket authentication and messaging, presence, rate limiting, read receipts, database models/migrations, frontend state/rendering, pagination/recovery, load-test tooling, test infrastructure, configuration, dependency declarations, and CI definitions. Existing documentation was cross-checked where it describes current behavior; roadmap items were excluded.

Production firewall rules, proxy sanitization, logging, secret strength, and sustained multi-worker capacity were not verified. A fresh full-history secret scan was not run. The vulnerability audit covered pinned application requirements, not every possible load-test dependency resolution. These checks cannot establish the absence of all other defects.

## Suggested first remediation pass

1. Reproduce and address H-01 through H-06, prioritizing authorization and destructive seed behavior.
2. Repair message persistence acknowledgement, gap recovery, read receipts, and history ordering together with focused regression coverage.
3. Address pagination, startup recovery, privacy, uploads, and registration validation failures.
4. Correct test-tooling and API-schema contracts.
5. Verify deployment-dependent risks and measure the identified performance concerns.

This sequence groups existing defects for practical work; it does not add proposed features or change the scope of the audit.
